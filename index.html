KEY INSIGHT / KEEP THE WORKLOAD MANAGER AVAILABLE

When the main agent does more execution,
the workload tends to wait longer.

The main agent controls task intake. When it spends time inside foreground execution steps, it can delay accepting new work. In the recorded trials, a larger main-agent execution share is associated with lower delivery and coverage.

02 / EVALUATE THE WHOLE WORKLOAD

New tasks arrive.
The agent keeps working.

In stream execution, an external dispatcher releases tasks over time. The agent sees released work, claims the next task, and organizes execution through its tools and subagents.

All tasks share 4 CPUs, an 8 GiB allocation, and one workspace. Independent verifiers score final artifacts. Self-reported completion is not correctness.

Tasks arrive over time; one agent system manages the shared workload.

05 / LOOK INSIDE EXECUTION

Taking on work is
a critical part of the job.

Serial intake leaves work behind

GLM serial FIFO leaves 73.3% of released heavy-tier tasks unclaimed. Fixed k = 2 reaches 42.8% SR, compared with 44.4% for native management.

Failure can vary between repeats

On the same thirty-task workload, the preprint records 30, 6, and 30 final reported completions. A strict six-hour cutoff gives 30, 5, and 30: the low repeat's sixth completion is late. These are reported completions, not verifier successes.

Who executes the work matters

In the pre-rebuttal analysis, a 10-percentage-point increase in the main agent’s share of execution tool calls is associated with 3.9 points lower per-trial reward and 5.2 points lower claim coverage, after centering within workloads. Tasks arriving during a foreground execution step wait a median of 2.0× longer to be claimed than other tasks in the same trial.

Scope, scoring and version notes

These are results for model–harness pairs, not model-only rankings. Ten medium workloads and five heavy workloads bound inference; heavy confidence intervals are coarse. Workloads contain no explicit task dependencies, values or priorities. Individual execution is a capability reference, not an equal-resource baseline.

Scoring excludes eleven tasks whose verifiers cannot validly judge execution, and gives no credit to completions after a sampled memory overrun. Historical trials include post-limit activity and shared-artifact effects. This page preserves manuscript snapshot d9e71fa, before the rebuttal revision; it does not mix in revised rebuttal scores. The current released code may contain subsequent engineering fixes. The thirty-task analysis is a case study.

06 / FOUR FAILURES, MADE CONCRETE

What does failure
actually look like?

A queue left behind. A first task that consumes the run. Unstable repeats. A missed hard constraint. These selected records explain distinct failure modes, not how often each system fails.
